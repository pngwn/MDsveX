Four ways to extend a document

mdsvex has two customisation surfaces today, directives and parse plugins. Two more are proposed: static directives, and plugins that own a directive. This page puts all four side by side: what each one is, where it acts, and what it can't do.

Where each one acts

One document, four stages

  1. You write markdown

    Directives are the only extension syntax. Everything else works on plain markdown.

    :::name[label](args)

  2. The parser builds the tree

    Handlers run as each node opens and closes, in the parser's single pass.

    Parse plugins annotate, retag and add nodes Handlers bound to a directive rewrite its children

  3. Compile writes Svelte

    Each directive resolves to a component by name.

    Live: a component instance Static: the component's HTML, rendered at build time

  4. The page runs

    What reaches the browser.

    Live directives hydrate and can hold state Static directives are plain HTML, with no code shipped

Directives

A name in the markdown that renders a Svelte component. This is how an author asks for something markdown doesn't have.

FormMarkdownThe component gets
Inline:abbr[HTML](title=HyperText)args, and the bracket text as children
Leaf::youtube[A talk](id=dQw4w9WgXcQ)args, and the bracket text as label
Container:::Callout[Heads up](kind=warn) … :::args, label, and the body as children

Register it

// src/lib/markdown.js
export * as directives from './directives.js';

// src/lib/directives.js
export { default as Callout } from './Callout.svelte';

Write it

<script>
  let { kind = 'note', label, children } = $props();
</script>

<aside class="callout {kind}">
  {#if label}<strong>{@render label()}</strong>{/if}
  {@render children?.()}
</aside>

What it can do

  • Anything a Svelte component can: state, effects, context, transitions.
  • Render the label and body wherever it likes.
  • Come from a template, which takes precedence over the root modules.

What it can't do

  • See or reshape its children. They arrive as one opaque snippet.
  • Take expressions as args. Values are always strings.
  • Go unregistered. An unknown directive is a compile error with its line and column.
proposed

Static directives

The same directive and the same component, rendered once at build time. Many directive components exist only because a component is a nicer way to write HTML. A callout has no state, yet every instance is imported, created and hydrated. Static mode writes its HTML straight into the page.

A shell with holes

A directive's body is markdown, and it can hold live content like {gap}. So the component is rendered as a shell, with a hole where each snippet goes. The document's own markup fills the holes and stays live.

Opt in where it's registered

// a site's own directives
mdsvex({ static_directives: ['Callout', 'badge'] })

// a plugin's directives
directives: {
  steps: { static: true, children: { … } },
  step: { static: true },
}

How it runs

  • The Vite plugin renders one shell per component and set of args, before compile.
  • compile() stays synchronous. It gets the shells as data, like src= files.
  • Outside Vite there are no shells, so every directive compiles live. Static never changes what a document means.

What it gives you

  • No component code shipped for that directive.
  • No hydration work for it.
  • Static directives nest: a static steps holds static step shells.

What the component gives up

  • State, effects, event handlers and transitions.
  • Context. It's rendered alone, so a parent and child can't coordinate. Tabs stays live.
  • Freedom with snippets. Each must render exactly once, unconditionally.

Parse plugins

Handlers keyed by node type that run while the tree is built. This is how you change what plain markdown produces, without the author writing anything.

Write it

const heading_ids = {
  heading: {
    parse(node, ctx) {          // the node opens
      return () => {            // the node closes
        node.attrs.id = slug(node.text_content);
      };
    },
  },
};

Register it

mdsvex({ parse_plugins: [heading_ids] })

All plugins are fused into the builder's one pass. sequential: true gives a plugin its own pass afterwards, when it needs the whole document.

What it can do

  • Read any node it can reach: parent, first_child, next, text_content.
  • Write attrs and type on those nodes.
  • Add nodes inside a node: wrap_inner, prepend, append.
  • Handle a directive that has no component.

What it can't do

  • Add syntax, remove nodes, or walk the tree.
  • Group siblings under a new parent.
  • Supply a component.
  • See a directive that has a component.
  • Rewrite text, read frontmatter, write metadata, or report a warning.

Grouping siblings is proposed for every plugin, as wrap_from. Supplying a component and reaching inside a directive that has one are what the next surface adds. The last line of the list is tracked in the plugin audit (plugins/PLUGIN_AUDIT.md §4).

proposed

Plugins that own a directive

One package that claims a directive name, supplies its component, and reshapes what the author wrote inside it. The plugin rewrites the children into ordinary directives, so the renderer needs nothing new.

Each step is a normal container directive. Step.svelte gets the heading as label and the rest as children. The heading is still a heading, so it keeps its id and its place in the table of contents, and the source reads as plain headings on GitHub.

Three additions make it possible

A bundle

A new plugins option takes one package: the module its components are exported from, and an entry for each directive name it owns.

Handlers bound to the directive

An entry's children handlers are called only for nodes written directly inside that directive, so they never check a parent. Each call gets an index (0 for the first) and a state object that is fresh for every directive.

wrap_from

One new tree method, available to every plugin. It wraps a node and the siblings after it in a new parent, which stays open until close() or until the enclosing node closes. Sectionize is a global plugin that needs it too.

The plugin

export function steps() {
  return {
    name: 'steps',
    module: '@mdsvex/kit/steps/directives',
    directives: {
      steps: {
        static: true,
        children: {
          // only headings directly inside :::steps
          heading(node, ctx) {
            ctx.state.step?.close();
            ctx.state.step = node.wrap_from(
              'directive_container', { name: 'step' });
            node.wrap_from('directive_label').close();
          },
        },
      },
      step: { static: true },
    },
  };
}

ctx carries directive, index and state. A :::steps nested in another gets its own. Global plugins still see these headings, so they keep their ids.

The site

mdsvex({ plugins: [steps()] })

The components

<!-- Steps.svelte -->
<ol class="steps">{@render children()}</ol>

<!-- Step.svelte -->
<li>
  {@render label()}
  {@render children?.()}
</li>

A site can replace either component by exporting its own steps or step. The rewrite still runs, so the replacement gets the same label and children.

This is the same rewrite tabs, accordions and code groups need, where the labels render apart from the panels. Live or static is a separate choice for each directive in the result: steps can be static, tabs has to be live.

In practice

Which one to reach for

  • A callout, a badge, a keyboard keyA directive, set to static. It's HTML with a nicer authoring interface.
  • A video embed, a chart, anything with stateA directive, live.
  • Steps, an accordion, a code group from plain headingsA plugin-owned directive. Steps can be static.
  • TabsA plugin-owned directive, live. The tab list and panels coordinate at runtime.
  • Heading ids, rel on external links, a class on every tableA parse plugin. The author writes nothing.
  • A different <table> or <img> everywhereAn element component, below.

Not settled

Open questions on the two proposals

Overrides

If a site replaces a plugin's component, does the plugin's rewrite still run? The draft says yes.

Compiler reuse

The reusable compiler falls back to a one-shot path whenever plugins are set. A common kit would cost every document that fast path.

Which headings split

The shallowest level among the direct children, a fixed level, or an arg?

Blocks inside a label

A label holds inline content today. The rewrite puts a heading in it.

Styles for static directives

The page no longer imports the component's code, which is what brings in its scoped CSS.

Rendering during a build

The dev server can load a component for server rendering. A production build has no dev server.

Where static is declared

On the registration, by a marker the component exports, or both?

wrap_from is unproven

It looks feasible next to how wrap_inner redirects children, but nobody has prototyped it.
